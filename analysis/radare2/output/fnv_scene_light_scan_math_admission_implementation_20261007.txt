Scope: correction of exact code admission only, not traversal, arithmetic or
another mod. The supported native identity, installed leaf bytes, copy extents
and leaf ABI are preserved in fnv_scene_light_scan_math_compatibility_contract_20261007.txt.
Those native bytes and deployed leaf buffers were rechecked before embedding.
The three alternative files contain the exact copied leaves plus native tails:
normalize_inlined.bin 118 bytes = 100 leaf + 18 tail;
vector_length_inlined.bin 69 bytes = 49 leaf + 20 tail;
vector_sqrt_inlined.bin 20 bytes = 7 leaf + 13 tail.

Production contract:
NativeRange retains its native expectation/owned-overlay behavior. It may also
hold one immutable full-range alternative. Only the three scan math statics use
that option. Preparation checks equal extents, prohibits combining an alternative
with owned overlays, and validates either complete supported body. Runtime
matches first compares the native/owned expectation, then the optional complete
alternative. A later PostPostLoad replacement can be admitted even if initial
preparation saw vanilla. No observed bytes are copied into an expectation.
Cold diagnosis reports unsupported ranges only and chooses an alternative with
the observed entry byte for its detailed mismatch when appropriate.
Both the hot and cold boundary continue rejecting every unknown byte, including
untouched native tails. They do not rewrite installed arithmetic or callbacks.

Behavioral evidence:
.reports/fnv_scene_light_scan_math_admission_regression_20261007.txt retains the
fail-first and passing Wine output. The actual production checker ran against
owned mappings containing verified native and installed code. The test-only
relocation changes only the address; production range configuration is retained.
Before correction, already-inlined preparation and post-preparation replacement
admission failed. After correction, both pass for all three ranges, as does
restoration to vanilla. Mutating every byte of each complete accepted input
rejects in preparation, hot comparison and diagnosis. Native math and traversal
are not executed by this memory-admission test; there is no modeled scene.
The complete affected core suite passed and the supported release target built.

Source-level work budget:
The three math extents are aligned and contain 29+17+5 DWORD reads plus 2+1
trailing byte reads on a matching vanilla input. The exact installed alternatives
have different first DWORDs, so their successful checks add one failed native
DWORD read per installed math variant, at most three additional engine DWORD
reads per pass. There is no per-advance change, lock, allocation, logging,
provider rewrite or FP arithmetic in qualification. This is a bounded memory
comparison cost, not an FPS result.

Startup scope:
The optional immutable alternative field changes private core NativeRange
static layout, and three small read-only byte ranges are embedded. No new owner,
TLS, worker, dependency, import, config field or callback is introduced. Existing
pre-CRT preparation order and owned bridge installation are retained. Bounded
comparison with the deployed core found its imported DLL/symbol sequence, TLS
data extent/section and callback identities unchanged. The callback identities
are Rust's Windows TLS guard, __dyn_tls_init, __dyn_tls_dtor and __dyn_tls_pthread.
Layout/code addresses still move; this is not a load-to-gameplay safety result.
The old deployed core has not been replaced and no release/package/commit was
created. Full Proton startup and native scan behavior remain untested.
