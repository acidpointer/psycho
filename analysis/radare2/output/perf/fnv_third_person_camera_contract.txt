3. Player update ordering
-------------------------

PlayerCharacter's main update is 0x0093E860.

Observed order relevant to Atom:

  0x0093F8D9  calls 0x009445B0, the player camera/input helper
  0x0093FA08  calls PlayerCharacter::UpdateCamera at 0x0094AE40
  0x0093FC3B  loads the 16-bit movement flags produced for this frame
  0x0093FC43  loads player +0x190, actorMover
  0x0093FC52  loads actorMover vtable
  0x0093FC54  loads virtual slot +0x0C
  0x0093FC57  commits the movement flags through that virtual call

Therefore normal player look/facing work precedes camera construction, and the
final actorMover flag commit follows camera construction. This ordering is a
direct observation. It does not establish where analog magnitude or the final
actor-local locomotion request is consumed.


4. Vanilla horizontal facing path
---------------------------------

In the normal third-person route, 0x009445B0 turns horizontal look input into a
call at 0x00945F90:

  0x00945F90  call 0x00931D30

0x00931D30 has this established x86 ABI:

  thiscall(PlayerCharacter *player, float deltaYaw) -> void

Selected instructions:

  0x00931D39  push 0
  0x00931D3E  load player vtable
  0x00931D43  load virtual +0x2BC
  0x00931D49  call current-yaw getter
  0x00931D4B  add deltaYaw
  0x00931D5B  load player vtable
  0x00931D60  load virtual +0x2C4
  0x00931D66  call yaw setter

This proves that normal vanilla horizontal look changes the player's
authoritative facing, not merely a camera-only yaw. Special vanity/free-camera
branches in 0x009445B0 instead update separate camera globals. Atom must not
fake those special flags to obtain free orbit.

0x00931D70 is not a yaw getter. It calls 0x00430830 and loads the first float
of the returned transform, Actor +0x24 rotX. Its paired setter at 0x00931D90
clamps that value and calls 0x00575770. The vertical look helper 0x00931E50
adds its input to 0x00931D70 and calls that setter. This directly establishes
0x00931D70 as raw pitch and invalidates the earlier yaw interpretation.


5. PlayerCharacter::UpdateCamera entry and VATS ownership
---------------------------------------------------------

PlayerCharacter::UpdateCamera is 0x0094AE40.

Entry snapshots:

  0x0094AE70  push 0
  0x0094AE80  load virtual +0x2BC
  0x0094AE86  call adjusted horizontal-heading getter
  0x0094AE88  store heading at 0x011E076C
  0x0094AE94  call 0x00931D70, raw Actor rotX/pitch
  0x0094AE99  store pitch at 0x011E0764

The normal matrix path closes the axis meanings independently of field names:

  0x0094B12D  load 0x011E076C
  0x0094B139  call 0x004A0C90, the native Z/yaw matrix builder
  0x0094B13F  load 0x011E0764
  0x0094B14E  call 0x00524AC0, the native X/pitch matrix builder

PlayerCharacter's vtable is 0x0108AA3C. Slot +0x2BC is therefore the pointer
at 0x0108ACF8 and resolves to 0x00953F20 in the supported executable.
0x00953F20 calls Actor adjusted-heading 0x008BD7B0, adds the player camera-only
offset at +0x6E4, and normalizes the result through 0x004B1480. A second
UpdateCamera call through the same slot occurs at 0x0094B444 and feeds another
native Z/yaw matrix. Both calls require the logical view heading while Atom
owns normal third person.

VATS branch:

  0x0094AF4B  set this to VATSCameraData at 0x011F2250
  0x0094AF50  call the VATS-mode getter
  0x0094AF55  compare mode with 4
  0x0094AF58  branch to normal path when mode is not 4
  0x0094AF64  read player +0x64C, bThirdPerson
  0x0094AF6D  branch to normal path when not third person
  0x0094AF73  begin copying VATS camera position and transform data
  0x0094AF73..0x0094B0E1  construct/commit the VATS-owned camera transform

The VATSCameraData mode field is +0x08. Established xNVSE behavior names the
observed values as:

  0  no VATS camera state
  1  target selection
  2  limb/zoom selection
  3  transition state with incomplete public semantics
  4  playback

0x00525430 returns whether the VATS mode is nonzero. It is called from player
input paths. UpdateCamera's direct VATS-camera transform is restricted to mode
4, but Atom must treat every nonzero mode as native ownership because the input,
targeting, and transition states begin before playback.


6. Normal third-person construction and settings
-------------------------------------------------

The normal third-person branch begins in the 0x0094B394 region after checks of
player +0x64A, +0x64C, and additional camera/player state.

Direct game-setting references in UpdateCamera include:

  fOverShoulderStartBlendDist  setting object 0x011CD844
    xrefs: 0x0094B599, 0x0094B5B2

  fOverShoulderPosX            setting object 0x011CDC5C
    xrefs: 0x0094B610, 0x0094B660

  fOverShoulderPosZ            setting object 0x011CDC44
    xrefs: 0x0094B5FA, 0x0094B632

  fOverShoulderRotMult         setting object 0x011CDDFC
    xref: 0x0094BB23

  fChaseCameraMax              setting object 0x011CD568
    used by the camera distance helper

The branch builds matrices and several local three-float vectors, then calls
0x0094A0C0 at 0x0094B7D2.

Callsite setup:

  0x0094B7B9  push byte argument from UpdateCamera arg_8h
  0x0094B7BE  push address of local vector at var_138h
  0x0094B7C5  push address of local vector at var_12ch
  0x0094B7CC  load PlayerCharacter this
  0x0094B7D2  call 0x0094A0C0

Proven ABI and semantics:

  thiscall(
    PlayerCharacter *player,
    Vec3 *desired_camera_in_out,
    const Vec3 *pivot,
    bool mode
  ) -> void

  callee return: ret 0x0C

At 0x0094B78A..0x0094B7B4, var_138h is built from the player's logical
position fields +0x30/+0x34/+0x38. It is the ray origin/pivot. Earlier matrix
and shoulder work at 0x0094B6F0..0x0094B72E builds var_12ch as the desired
camera endpoint.

Inside 0x0094A0C0, the helper subtracts pivot from desired, measures and
normalizes that direction, passes pivot and desired to the collision query,
then reconstructs:

  resolved = pivot + normalize(desired - pivot) * resolved_distance

At 0x0094A88C..0x0094A8A6 it copies the resolved three-float vector back only
through desired_camera_in_out. No instruction writes through pivot. The mode
byte remains a value argument.

After the call:

  0x0094B7F9..0x0094B811  copies the var_12ch vector into another camera local
  0x0094B85D..0x0094B876  writes a computed vector to player +0xD58
  later code combines camera offsets, pitch, rotation multipliers, and the
  helper's collision/distance state before committing the camera object

The production composition rule is direct: axial follow and bounded motion
alter only the desired endpoint passed at 0x0094B7D2. Preserve the exact native
player-root pivot and mode byte, chain the live 0x0094A0C0 predecessor exactly
once, and copy its resolved desired endpoint back. Do not retain either
stack-local pointer beyond the call.


7. Native third-person collision and distance helper
-----------------------------------------------------

0x0094A0C0 has two callsites:

  0x0058D201
  0x0094B7D2 in PlayerCharacter::UpdateCamera

Direct observations:

  - It receives PlayerCharacter as this and two vector pointers plus a byte.
  - It reads player +0x64A and +0x64C to classify camera transition/state.
  - It reads the world/collision owner at player +0x21C.
  - It prepares two local endpoints from its vector arguments.
  - It calls 0x00620BC0 through player +0x21C at 0x0094A344.
  - It resets 0x011E07C2 before the query and sets it when the collision result
    constrains the available camera distance.
  - It updates and clamps the current distance state at 0x011E0768.
  - It consults fChaseCameraMax through setting object 0x011CD568.
  - It has special behavior when VATS mode is 4.
  - It transforms a vector using the resolved 0x011E0768 distance near
    0x0094A598..0x0094A5BC.

Selected collision sequence:

  0x0094A29B  copy one endpoint from the second vector argument
  0x0094A2A0  copy the other endpoint from a prepared local
  0x0094A2C0  read player +0x21C
  0x0094A32C  begin pushing query outputs and endpoints
  0x0094A344  call 0x00620BC0 through player +0x21C
  0x0094A374  set 0x011E07C2 when the available distance is constrained
  0x0094A409..0x0094A598  update/clamp 0x011E0768

The helper owns both inward contraction and outward recovery through current
distance state 0x011E0768. No separate recovery hook is needed for the initial
implementation. A camera-space offset applied only after UpdateCamera returns
would bypass this resolution and can place the camera inside geometry; Atom
must compose the desired endpoint before this helper and preserve it
downstream.

Normal third-person final-offset proof:

  0x0094B9E6  read collision result byte 0x011E07C2
  0x0094BA53  no-collision branch begins reading normal offset settings
  0x011CDA34  fOverShoulderOffsetPointX setting object
  0x011CDFB4  fOverShoulderOffsetPointY setting object
  0x011CD31C  fOverShoulderOffsetPointZ setting object
  0x0094BAB8  build X/pitch matrix from 0x011E0764
  0x0094BAD1  transform the selected offset by pitch
  0x0094BB04  transform that result by the already-built Z/yaw matrix

The X builder 0x00524AC0 and vector transform 0x004B4500 prove the exact
mapping `x'=x`, `y'=cos(pitch)*y + sin(pitch)*z`,
`z'=-sin(pitch)*y + cos(pitch)*z`. The existing camera yaw mapping is then
applied after the native clearance query.

Runtime rejection, 2026-08-19: feeding this post-collision offset backward by
translating both query endpoints preserves ray length but changes the world
segment and its hit set. Proton showed new contractions against tables, small
objects, walls, and actors in close interiors, without fixing the heading
reset. The collision helper updates the desired endpoint, distance state
0x011E0768, and result byte 0x011E07C2; it does not own view yaw. Atom must keep
the native pivot exact and must not use collision geometry to address a yaw
ownership failure.

Final transform proof:

  0x0094BB61  address of resolved camera local var_60h
  0x0094BB65  camera object 0x011E0C20 as this
  0x0094BB6A  call 0x00440460

0x00440460 copies the three floats to camera +0x58. Rotation is committed
later through 0x00A59C60 at 0x0094BB90. This is the final native position seam,
not an admitted post-collision edit point.


8. Movement flags, vector carrier, and downstream ownership
------------------------------------------------------------

PlayerCharacter::Update builds a 16-bit flag local at [ebp-0x6C]. Direct
keyboard action branches prove the low direction bits:

  0x00941C05  action 0, forward       OR 0x01
  0x00941C5B  action 1, backward      OR 0x02
  0x00941CB1  action 2, slide left    OR 0x04
  0x00941D08  action 3, slide right   OR 0x08

Controller sign branches at 0x009412D1..0x0094134C and
0x009414BE..0x00941550 produce the same bits. The direct executable evidence
supersedes an ambiguous xNVSE comment that names low bit 0 as keep-moving.
Established higher bits remain:

  0x0080  walk
  0x0100  run
  0x0200  sneak
  0x0400  toggle/keep-move state
  0x0800  swim

The final flags are committed through actorMover virtual slot +0x0C at
0x0093FC57. PlayerMover's vtable is 0x0109297C and +0x0C resolves to
0x009EA3E0. That setter stores the full word at PlayerMover +0x94. Its only
conditional work compares bit 0x0400 and masks bits 0x0030; no branch or call
depends on low direction bits 0x000F. Atom must not replace or synthesize this
native publication path.

Analog and movement-vector construction:

  - controller axes 7, 9, and 8 are sampled at 0x00941111,
    0x00941123, and 0x00941135;
  - dead-zone and normalization work feeds scalar 0x011A3B3C;
  - that scalar multiplies the native speed at 0x009418A8 and
    0x00941B71..0x00941B98;
  - the final native movement vector is local var_1E0h.

The earlier ledger revision attributed a horizontal transform in this path to
0x00931D70. Exact axis closure disproves that attribution: 0x00931D70 is the
Actor rotX/pitch getter. The vector reaching player virtual +0x250 remains
actor-local because its nested callee performs the actor-heading-to-world
transform described below; Atom does not depend on a semantic name for every
intermediate var_1E0 producer.

Vector carrier:

  0x009427FB  push &var_1E0h
  0x00942805  ECX = player->actorMover at +0x190
  0x0094280B  call 0x009EA570
  0x00942830  immediately call PlayerMover virtual +0x14 with dt

0x009EA570(Vec3 const *) copies exactly three floats to PlayerMover +0x88 and
returns with ret 4. Its only direct callsites are 0x0093FEB8, 0x0094280B, and
0x00947591. This proves the carrier but is not the final Atom seam because the
PlayerMover still applies low-direction diagonal policy afterward.

PlayerMover virtual +0x14 resolves to 0x009E9E50. It starts with the native
movement vector, checks low flags at +0x94, and, on its normal movement path:

  - measures PlayerMover +0x88 and the native vector;
  - normalizes the +0x88 direction and restores the native vector magnitude at
    0x009E9FE8..0x009EA05F;
  - applies the forward/back and left/right diagonal policy from flags
    0x01/0x02 and 0x04/0x08 at 0x009EA062..0x009EA1B9;
  - calls PlayerCharacter virtual +0x250 with dt, the resulting Vec3, and the
    unchanged flags at 0x009EA207..0x009EA232.

The PlayerCharacter vtable begins at 0x0108AA3C. Its +0x250 slot at 0x0108AC8C
contains 0x008A62B0. This complete wrapper has the ABI:

  thiscall(
    PlayerCharacter *player,
    float dt,
    Vec3 *movement_in_out,
    uint32_t movement_flags
  ) -> process pointer

  callee return: ret 0x0C

At 0x008A62D9 it begins native actor gating. At 0x008A62E8 it masks the
supplied flags with 0x3F and can return before the nested movement request.
After further actor/process gates it pushes the same flags, Vec3 pointer, and
dt, then calls 0x0092F260 at 0x008A6339:

  thiscall(
    MobileObject *actor,
    float dt,
    Vec3 *movement_in_out,
    uint32_t movement_flags
  ) -> process pointer

  callee return: ret 0x0C

0x0092F260 copies all four inputs into a native movement request at
0x0092FCD5..0x0092FD2B and again on an alternate path at
0x0093034F..0x009303A5. The request layout proven by stores is:

  +0x00  dt
  +0x04  actor rotation Vec3
  +0x10  movement Vec3
  +0x1C  movement flags
  +0x24  admission byte

It then performs the existing actor-heading transforms, controller/scene work,
physics and position updates, request dispatch, and transform application
before final 0x00575830 at 0x00930475. Vector and direction flags therefore
enter animation/physics/root-transform ownership together at one call.

For the live player, 0x0092F260 selects raw rotZ through 0x0080F790 instead of
virtual +0x2BC. 0x0080F790 reads the third transform float at Actor +0x2C.
At 0x0092F538..0x0092F574 and again at 0x009302C5..0x0093030D, the request:

  1. builds a Z matrix with 0x004A0C90 from that raw actor heading;
  2. applies it to the incoming Vec3 through 0x004B4500; and
  3. writes the transformed result back to the request vector.

The proven matrix rows are `[cos, sin, 0; -sin, cos, 0; 0, 0, 1]`. Therefore,
for local input L and heading h, define:

  E(h) * L = (
    cos(h) * L.x + sin(h) * L.y,
   -sin(h) * L.x + cos(h) * L.y,
    L.z
  )

Local +Y is forward and becomes `(sin(h), cos(h))` in world space. This closes
the vector supplied to virtual +0x250 as actor-local and makes raw rotZ, not
adjusted camera heading, the downstream transform authority.

PlayerMover consumes the movement word before the late movement request:

  0x009E9F95  first read mover +0x94 and mask the low direction nibble
  0x009EA062  split forward/back bits from left/right bits
  0x009EA11B  left/right bits alter the prepared local movement vector
  0x009EA20D  call 0x008846E0 for the complete flags passed to the player
  0x009EA232  call player virtual +0x250 with that prepared vector
  0x008A62E8  wrapper consumes flags before its nested request
  0x008A6339  nested actor movement request inside the +0x250 path

Runtime rejection, 2026-08-19: PlayerMover +0x88 is not the direction passed to
the player wrapper. The function initializes its output from global/native
state at 0x009E9E5D, may replace it through native helpers, and uses +0x88 only
inside its magnitude/override normalization. Treating +0x88 as final direction
rotated Actor facing by a constant 90 degrees in Proton.

Runtime rejection, 2026-08-19: splitting ownership between the getter at
0x009EA20D and nested call at 0x008A6339 is not coherent. The getter ABI has no
movement-vector argument, so it classified flags against pre-turn Actor yaw.
The nested hook then changed Actor yaw and the vector after the complete wrapper
had already consumed those flags. Proton showed cardinal input collapsing into
diagonal presentation.

Runtime rejection, 2026-08-19: correcting only the flags argument of the
complete +0x250 wrapper did not correct the visible cardinal family at a
90-degree camera/body offset. That Proton result rejects the wrapper-only
candidate; it does not by itself prove which later animation consumer selected
the wrong family.

Runtime rejection, later 2026-08-19: writing Atom's selected low nibble to
PlayerMover +0x94 after PlayerMover::Update returns is not an animation fix.
There is no later +0x94 read between the +0x250 call at 0x009EA232 and the
0x009EA2E6 epilogue. The write therefore cannot affect the animation selected
for that invocation. Instead it survives as input to the next invocation,
whose first low-nibble read is 0x009E9F95 and whose direction-dependent vector
work continues through 0x009EA1B9. Repeated or overlapping A/D input exposed
stale lateral feedback, incorrect movement, and coupled camera/body rotation
in Proton. PlayerMover +0x94 is an input/state word, not a safe late
presentation seam; Atom must never publish its derived animation sector there.

The PlayerCharacter +0x250 vtable slot is a coherent movement seam: it is the
first callable boundary where the finalized post-PlayerMover Vec3 and complete
flags are available together, before any wrapper consumer. It is not the
presentation seam. PlayerCharacter::Update selects directional locomotion
earlier:

  0x009422D1  load the current movement byte from local var_6Ch
  0x009422D9  call 0x00894F90 with PlayerCharacter and that byte
  0x00894FC4  test forward bit 0x01 and select group 11
  0x00894FD6  test backward bit 0x02 and select group 12
  0x00894FE8  test left bit 0x04 and select group 13
  0x00894FFA  test right bit 0x08 and select group 14
  0x00895017  resolve the active animation group through the live actor path

This is the current-invocation visible animation selector. Its direct callsite
is the safe presentation seam: Atom may replace only the low direction nibble
in that call's value and chain its captured live predecessor exactly once. The
selector runs before the complete movement wrapper, so its body-relative
classification uses the current raw Actor yaw and the retained logical view.
It must not write PlayerMover state, call a skeleton correction node, or alter
Combat flags. The rejected late +0x94 write is removed rather than relocated.

Derived mapping with the native matrix convention:

  desired_world = E(view_heading) * local_input
  request_local = E(view_heading - request_actor_heading) * local_input
  native_world  = E(request_actor_heading) * request_local
                = desired_world

Explore turns the actor toward nonzero desired_world and gives the complete
player wrapper the matching native eight-way low nibble. Combat turns the actor
toward the view and retains the original low nibble so native
forward/back/strafe intent stays correct around that facing. All unsupported
states preserve the original vector and complete flags. The derived nibble may
be passed to 0x00894F90 only at its proven PlayerCharacter callsite. It must
not be written back to PlayerMover state. Atom does not alter analog magnitude
or any skeleton/root transform.

The order is part of the contract. Atom first computes desired world heading
from `E(view_heading) * local_input`, advances and writes Actor facing, samples
the resulting raw rotZ, compensates the vector, and selects the sector from
`heading(desired_world) - actual_actor_heading`. Forward, left, right, and
diagonal presentation consequently describe physical travel relative to the
post-turn body. The rejected split classified before that heading existed.

Lifetime:

  0x009E9D00 constructs PlayerMover from PlayerCharacter construction
  0x00964190 -> 0x0096421A. It installs vtable 0x0109297C, zeros Vec3 +0x88,
  flags +0x94, state +0x98, and initializes timer +0x9C. PlayerCharacter owns
  the mover through pointer +0x190. Atom validates the live player and mover
  every admitted update and retains neither pointer across load/reinit.


9. Native state predicates and transition ownership
----------------------------------------------------

All values below are sampled once before Atom output in the player update.
Failure or mismatch means native ownership for the complete frame.

POV and active 3D:

  player +0x64A  not-first-person/transition state used by UpdateCamera
  player +0x64B  active perspective/skeleton selector
  player +0x64C  requested/stable third-person state

0x00950BE0 proves +0x64B: false returns player +0x694, the first-person node;
true obtains the world 3D through 0x0043FCD0. Atom requires +0x64A, +0x64B,
and +0x64C all nonzero. Any mismatch is a native POV transition. The selected
3D must also be nonnull.

Other direct owners:

  0x011E07B8 nonzero                       special native camera owner
  VATSCameraData 0x011F2250 mode nonzero   all VATS states
  (*0x011DEA0C) +0x06 nonzero              TFC/isFlycam
  player +0x680 disabled flags             0x01 Movement, 0x02 Look,
                                            0x04 Pipboy, 0x08 Fight,
                                            0x10 POV
  player +0x108 nonzero                    non-alive life state
  process virtual +0x40C nonzero           knocked/ragdoll state
  player +0x68 null/insufficient process   missing process
  player +0x40 null                         missing parent cell
  player +0x21C null                        missing world/collision owner

0x00702360 is the exact broad MenuMode predicate. It requires the
InterfaceManager singleton at 0x011D8A80, tests its active byte through
0x009373F0, and then returns whether InterfaceManager +0x0C differs from normal
gameplay mode 1 through 0x007023A0. It therefore covers Pip-Boy, dialogue,
loading, pause, console, and text-entry menu ownership without enumerating
menu names. True means native ownership.

The +0x680 byte is vanilla ownership. xNVSE additionally tracks per-mod and
extended disabled controls. Atom uses the repository PlayerControls API's
combined `ByAnyModOrVanilla` query for Movement, Looking, Pipboy, and POV, plus
Fighting for combat/aim admission. This preserves external capability owners
instead of reading only vanilla state.

Furniture uses the process virtual at +0x4BC:

  0x0  normal
  0x1  load sit
  0x2  want sit
  0x3  waiting sit
  0x4  sitting
  0x5  stand
  0x6  load sleep
  0x7  want sleep
  0x8  waiting sleep
  0x9  sleeping
  0xA  wake

Every nonzero value is native-owned. Current animation action comes from
process virtual +0x3E4; 0x0D (Wait_For_Special_Idle) and 0x0E
(Force_Script_Anim) are also native-owned. The process virtual at +0x40C is
GetKnockedState and returns the live knocked/ragdoll state as a signed 32-bit
integer through the normal thiscall ABI.

Runtime correction, 2026-08-16:

  The original ledger incorrectly inferred that a nonnull Actor +0x0AC meant

camera collision callsite and camera-specific filtering; it is not a general
aim ray.

No-allocation convergence design derived from the proven boundaries:

  1. Scoped wrapper at 0x0070C130 supplies Atom's logical view origin and
     direction only during Atom-owned stable third person, then calls the live
     ViewCaster predecessor. In native states it passes the original arguments
     exactly.
  2. The wrapper publishes only fixed-size result data: origin, direction,
     supplied maximum, returned distance/hit classification, player identity,
     frame serial, and Atom camera ownership epoch. It performs no second cast.
     A hit requires finite out_distance in [0, max_distance]; FLT_MAX or an
     out-of-range result is no hit.
  3. At 0x005245BD the spawn wrapper requires a matching live player, ownership
     epoch, and logical view origin/direction. A valid reticle hit selects
     origin + direction * returned distance. No hit selects the same view ray
     extended to the effective projectile's native range.
  4. The wrapper resolves the real muzzle, computes muzzle-to-target base
     angles, reapplies the exact native sampled spread deltas, and calls the
     native spawn predecessor with the real muzzle position.
  5. The native projectile, starting at the real muzzle, owns near-cover
     collision. A wall between muzzle and target is hit by the normal subtype
     collision path, so no approximate generic muzzle ray can disagree with
     native transparency, actor, impact, or physical-projectile filters.
  6. Absent/stale epoch, missing player/caster/node/range, non-finite math, an
     unrecognized callsite, or an unsafe predecessor chains the original call
     unchanged.

The UI crosshair and player-fire paths are separate main-loop consumers. The
latest completed sample is admitted only when player, ownership epoch, origin,
and direction still match the current logical view; otherwise that shot stays
native. Runtime telemetry must establish whether same-frame or one-completed-
sample freshness is available across mouse/controller and frame-rate cases.
If it cannot, Phase 5 remains disabled rather than adding another allocating
ViewCaster call to the shot hot path.

19. Axis and movement correction after broken-build observation
---------------------------------------------------------------

exactly account for those symptoms:

  1. the artifact replaced 0x0094AE94 -> 0x00931D70 with logical view yaw,
     but 0x00931D70 is rotX/pitch; and
  2. movement compensation used the old actor heading, then wrote a new actor

the facing that will actually reach 0x0092F260. The public regression composes
Atom's compensated vector with the exact native E(actor) matrix for nonzero,
opposing, and wrap-boundary headings and requires equality with E(view) input.

20. Eight-way locomotion and linear wheel-distance contract
------------------------------------------------------------

Runtime baseline observation on 2026-08-16:

  atom.dll SHA-256: fa9194843522c4c130f2c829929716626012ac3e2e3cc7d054dd2006ae40ee0b
  user result:      third-person behavior "works pretty nice"

The installed artifact and target release artifact were byte-identical. This
is the accepted starting point for the new diagonal and zoom work, not evidence
that the new behavior has been accepted at runtime.

Native movement direction vocabulary already established at 0x0092F260:

  forward   0x01
  backward  0x02
  left      0x04
  right     0x08

The engine accepts cardinal bits and their forward/back plus left/right
combinations. Atom's camera-relative vector is already exact after composition
with the raw post-setter actor yaw. Therefore diagonal refinement requires no
new movement seam and must not alter that vector. The safe intervention is the
same proven low direction nibble: classify desired world movement relative to
the post-setter raw actor yaw, retain high flags, and leave Combat native.

Normal third-person wheel call:

  0x009459B3  6A 03 8B 8D D4 FE FF FF
              push axis 3; load the mouse/input receiver
  0x009459BB  call 0x00A239E0
  0x009459C0  89 85 D0 FE FF FF
              store the returned signed wheel delta

The call displacement itself is mutable and can be chained. The surrounding
instructions are the semantic fingerprint. This exact callsite is inside the
normal player-camera path, so other axis reads, menu input, and hotkeys remain
outside Atom's ownership.

Live operands consumed by the following native wheel calculation:

  0x011E0B5C  desired third-person distance
  0x011CDC98  fVanityModeWheelInMult setting object
  +0x04       float value, vanilla default 0.05
  0x011CD2AC  fVanityModeWheelOutMult setting object
  +0x04       float value, vanilla default 0.10

The direct calculation is:

  desired -= raw_delta / 120.0 * desired * direction_multiplier

The normal distance bounds observed in the same UpdateCamera route are 30 and
120, with initial desired distance 60. At 0x0094B6D3 native endpoint building
uses desired distance. The helper called at 0x0094B7D2 -> 0x0094A0C0 owns
collision and updates realized distance at 0x011E0768. Consequently linear
zoom must invert the native formula using 0x011E0B5C, never rebase on the
collision-contracted 0x011E0768 value.

The safe input transform is:

  adjusted_delta = raw_delta * world_units_per_notch
                   / (desired * direction_multiplier)

Native still performs the only distance write, clamps, POV decisions,
endpoint construction, collision contraction, and outward recovery. A
non-finite/nonpositive operand, a setting multiplier of zero, or an unavailable
hook must pass the original signed delta unchanged. These address and formula
facts are direct binary evidence. The two-unit default, 1..10 MCM bounds,
five-degree sector hysteresis, independent hook transaction, and fractional
residual policy are Atom design decisions.
